# Эксперт по гарантийным случаям ФЗ-214

## 1) Как должна работать система

### Входные данные
- Текст замечания (как от собственника).
- Тип объекта: квартира / МОП / фасад / инженерка.
- Дата передачи квартиры по акту.
- Дата обращения.
- Были ли вмешательства собственника (ремонт, перенос, сверление, замена окон/дверей, перенос мокрых зон, изменение вентиляции).
- Фото/видео (если есть).
- Документы: акт осмотра, претензия, ответ застройщика, результаты обследования/экспертизы (опционально).

### Выходные данные
- Классификация: гарантийный случай / не гарантийный / недостаточно данных.
- Вероятность (в процентах) + уровень уверенности.
- Обоснование по логике ФЗ-214 без выдуманных фактов.
- Какие данные отсутствуют для уверенного вывода.
- Рекомендованные действия (акт, обследование, экспертиза, устранение).
- Риски при переходе спора в судебную стадию.

## 2) Готовый промпт для LLM

Ниже шаблон, который можно использовать в ChatGPT/Claude/другой LLM.

```text
Роль:
Ты — узкоспециализированный эксперт по гарантийным обязательствам застройщиков по ФЗ-214. Твоя задача — определить, является ли дефект гарантийным случаем, и дать обоснование.

Ограничения:
- Не придумывай факты.
- Если данных недостаточно — перечисли, что нужно.
- Не используй общие фразы (“возможно”, “скорее всего”) без причины.
- Всегда давай итог: гарантийный / не гарантийный / недостаточно данных.
- Оцени вероятность в процентах.
- Отдельно оцени вероятность, что причина связана с эксплуатацией/вмешательством собственника.

Входные данные будут в формате:
- Дата передачи по акту:
- Дата обращения:
- Описание дефекта (замечание):
- Где находится дефект:
- Фото/видео: (да/нет + краткое описание или вывод vision-модуля)
- Были ли вмешательства собственника:
- Дополнительно:
- Доступные документы (акт/претензия/ответ/экспертиза):

Задача:
Сделай заключение по структуре ниже.

Формат ответа (обязательный):
1) Классификация:
   - Гарантийный случай / Не гарантийный / Недостаточно данных
   - Вероятность: __%
   - Вероятность эксплуатационной причины (ошибки/вмешательства собственника): __%

2) Ключевые факты из обращения:
   - (списком)

3) Анализ причин (техническая логика):
   - Возможные причины дефекта
   - Какие причины относятся к ответственности застройщика
   - Какие причины относятся к эксплуатации/ремонту собственника

4) Анализ по ФЗ-214 (логика гарантийных обязательств):
   - Сроки (гарантия на объект / инженерные системы)
   - Есть ли признаки строительного дефекта
   - Есть ли признаки эксплуатации/вмешательства

5) Нормативная проверка (СП/СНиП/ГОСТ):
   - Какие группы норм применимы к этому дефекту
   - Какие данные нужны для проверки соответствия нормам
   - Если точная ссылка на пункт нормы не подтверждена входными данными — явно так и напиши

6) Вывод (почему гарантийный или почему нет):
   - 3–6 тезисов строго по делу

7) Что нужно запросить дополнительно (если не хватает данных):
   - (списком)

8) Рекомендации по действиям:
   - Для собственника
   - Для застройщика
   - Нужно ли обследование/экспертиза

9) Контур обучения (обновление базы кейсов):
   - Какой исход дела нужно зафиксировать после фактического рассмотрения
   - Как этот кейс изменит будущие оценки
```

### Пример ввода

```text
Дата передачи по акту: 12.06.2023
Дата обращения: 03.02.2026
Описание дефекта: “На откосе окна появилась плесень и мокрое пятно”
Где находится дефект: кухня, окно
Фото/видео: да (на фото видна плесень по нижнему углу откоса)
Были ли вмешательства собственника: ремонт был, окна не менялись
Дополнительно: квартира угловая, 14 этаж
Доступные документы: акта осмотра пока нет
```

## 3) Как подключить фото/видео без перегруза контекста

### Шаг 1 — Vision-анализ
Vision-модель получает фото/кадр видео и выдает структурированный вывод:
- Тип дефекта: трещина / влажность / плесень / скол / течь.
- Локализация: стык, угол, потолок, окно.
- Масштаб: мелкий / средний / крупный.
- Признаки: протечка сверху, ржавые потеки, грибок, высолы.
- Вероятность категории.

### Шаг 2 — Юридическое заключение LLM
В LLM передается не сырой медиафайл, а сжатый структурированный результат Vision, например:

```text
Vision-вывод: на фото видны высолы и мокрое пятно на потолке вдоль шва плиты перекрытия, вероятная протечка 82%.
```

Так снижается шум и повышается стабильность юридического анализа.

## 4) Узкая специализация для стабильных ответов

Используйте ограниченный справочник категорий дефектов:
- Окна/откосы/промерзание.
- Протечки (кровля, стояки, межпанельные швы).
- Трещины (усадочные / конструктивные).
- Плитка, стяжка, полы.
- Электрика.
- Вентиляция.
- МОП и фасады.

Для каждой категории заранее определите:
- Что обычно относится к гарантии.
- Что обычно относится к эксплуатации.
- Какие уточняющие вопросы обязательны.

## 5) Самообучаемая система (на практике)

Цель: чтобы система учитывала реальные исходы споров и не смещалась в пользу только одной стороны.

### 5.1 Какие исходы фиксировать по каждому кейсу
После закрытия обращения добавляйте фактический исход:
- Подтверждено гарантийным (да/нет).
- Причина дефекта: строительная / эксплуатационная / смешанная / не установлена.
- Основание: акт осмотра, экспертиза, судебное решение, досудебное урегулирование.
- Кто устранял и за чей счет.
- Срок устранения.
- Повторяемость дефекта (рецидив).

### 5.2 Минимальная карточка кейса (для базы знаний)
```json
{
  "category": "окна_откосы",
  "defect": "плесень на откосе",
  "building_age_months": 32,
  "owner_interventions": ["ремонт"],
  "developer_fault_probability_initial": 0.78,
  "owner_fault_probability_initial": 0.22,
  "final_resolution": "mixed",
  "evidence": ["акт", "тепловизор"],
  "court": false
}
```

### 5.3 Как обновлять веса (простая схема)
- Для каждой категории храните счетчики исходов: `developer_fault`, `owner_fault`, `mixed`, `unknown`.
- Каждые 20–30 закрытых кейсов пересчитывайте базовые вероятности по категории.
- Если доля эксплуатационных причин растет, система должна поднимать вероятность `owner_fault` при похожих входных признаках.
- Никогда не менять вывод только по статистике: статистика корректирует приоритет гипотез, но не заменяет факты конкретного кейса.

### 5.4 Анти-смещение (важно)
- Запрещено автоматически считать собственника правым или неправым.
- При отсутствии доказательств итог: «Недостаточно данных» + список, что запросить.
- В каждом ответе обязательно отдельной строкой: «Признаки возможной ошибки/вмешательства собственника».

## 6) Нормативная база (СП/СНиП/ГОСТ) — как применять корректно

Важно: LLM не должна «памятью» подменять юридически значимый источник нормы.

### 6.1 Принцип работы
- Использовать только проверяемый реестр нормативов (внутренний справочник компании).
- Для каждого типа дефекта хранить:
  - группу применимых документов (СП/ГОСТ и др.),
  - актуальность редакции,
  - ссылку на официальный источник,
  - извлекаемые проверочные критерии.

### 6.2 Что делать, если точный пункт нормы не подтвержден
- Прямо писать: «Точный пункт нормы требует верификации по действующей редакции документа».
- Не выдавать непроверенный номер пункта как установленный факт.

### 6.3 Рекомендуемый регламент обновления
- Плановое обновление реестра: 1 раз в месяц.
- Внеплановое: при изменении нормативки или при спорном/судебном кейсе.
- Ответственный: отдельная роль (технорм-контролер/юрист).

## 7) Проверка на примере (демо-ответ модели)

Ниже пример того, каким должен быть итоговый ответ LLM на тестовый кейс выше.

```text
1) Классификация:
- Гарантийный случай
- Вероятность: 78%
- Вероятность эксплуатационной причины: 22%

2) Ключевые факты из обращения:
- Передача квартиры по акту: 12.06.2023.
- Обращение: 03.02.2026 (предварительно в пределах гарантийного срока на объект).
- Дефект: плесень и мокрое пятно на откосе окна.
- Локация: кухня, окно, нижний угол откоса.
- Квартира угловая, 14 этаж (повышенный риск мостиков холода/продувания узла примыкания).
- Собственник делал ремонт, окна не менялись.

3) Анализ причин (техническая логика):
- Возможные причины дефекта:
  - нарушение герметизации монтажного шва окна;
  - промерзание узла примыкания (мостик холода);
  - нарушение теплотехнического контура откоса;
  - повышенная влажность из-за режима эксплуатации (недостаточная вентиляция/сушка).
- Возможные причины в зоне ответственности застройщика:
  - дефект монтажа окна;
  - дефект утепления/герметизации откоса и примыканий;
  - строительный дефект наружного шва фасада в зоне окна.
- Возможные причины в зоне эксплуатации собственника:
  - систематически высокая влажность в помещении;
  - перекрытая или неработающая вентиляция после ремонта.

4) Анализ по ФЗ-214 (логика гарантийных обязательств):
- По сроку обращения случай предварительно попадает в гарантийный период для конструктивных элементов.
- Наличие плесени и мокрого пятна в зоне откоса указывает на возможный строительный дефект (герметизация/промерзание/протечка узла).
- Признаки вмешательства есть (ремонт), но ключевой элемент (окно) не заменялся, поэтому автоматического исключения гарантии нет.
- Для окончательного вывода нужно отделить строительную причину от эксплуатационной (влажностный режим).

5) Нормативная проверка (СП/СНиП/ГОСТ):
- Применимы группы норм по тепловой защите, оконным узлам примыкания и микроклимату помещений.
- Для точной проверки нужны: проектный узел, акт обследования, замеры температуры/влажности и результаты тепловизора.
- Точные пункты нормативов подлежат верификации по действующей редакции внутреннего реестра.

6) Вывод (почему гарантийный):
- Срок обращения не выходит за типичный гарантийный период по ФЗ-214 для объекта.
- Симптомы дефекта локализованы в типовой зоне строительных рисков (оконный узел примыкания).
- Прямых данных о нарушении конструкции окна собственником нет.
- Нужен акт осмотра и инструментальная проверка, но на текущих данных приоритетно рассматривать как гарантийный кейс.

7) Что запросить дополнительно:
- Акт первичного осмотра с фиксацией влажности/температуры/следов промерзания.
- Тепловизионное обследование узла окна (по возможности в холодный период).
- Проверка вентиляции кухни и квартиры (тяга, приток воздуха).
- Фото фасадного шва снаружи и внутренних примыканий откоса крупным планом.
- Историю обращений по аналогичным дефектам в этом стояке/секции.

8) Рекомендации по действиям:
- Для собственника:
  - направить письменную претензию с фотофиксацией и требованием осмотра в разумный срок;
  - обеспечить доступ для обследования;
  - не устранять следы дефекта до составления акта.
- Для застройщика:
  - провести комиссионный осмотр и составить акт с причиной дефекта;
  - при подтверждении строительной причины — выполнить гарантийное устранение;
  - при споре о причине — инициировать независимое обследование.
- Обследование/экспертиза:
  - желательно (объективирует причину и снижает риск судебного спора).

9) Контур обучения (обновление базы кейсов):
- После закрытия обращения зафиксировать финальную причину дефекта и основание (акт/экспертиза/суд).
- Если подтвердится эксплуатационная причина, увеличить вес owner_fault для аналогичных кейсов.
- Если подтвердится строительная причина, увеличить вес developer_fault для аналогичных кейсов.
```

> Важно: демонстрационный ответ не заменяет техническое обследование. Итоговая квалификация должна подтверждаться актом осмотра и (при споре) независимой экспертизой.
